# LAN-696 레퍼럴 관리.

기준은 LAN-696 승인 설계다. 별도 Figma 프레임 없이 기존 어드민 셸·카드·폼·확인 대화상자를 사용한다.

- `/referrals`에서 가입 완료와 첫 실제 결제 보상의 활성화, 대상, 초대인·피초대인 금액을 독립 편집한다.
- 금액은 수령자별 1~1,000,000원 정수다. 비활성/비대상 금액은 0으로 보낸다.
- 결제 대상 상품은 RevenueCat 앱·스토어·상품 ID·구독/일회성 유형을 입력한다. 결제 보상 활성화 시 하나 이상 필요하다.
- 변경 사유를 입력하고 변경 전후를 확인한 뒤 저장한다. 코드 등록 시 두 단계의 대상·금액·상품이 고정되고 변경된 단계 정책은 이후 등록자부터 적용된다. 초대인 한도는 기존 관계의 미지급 보상에도 다음 지급부터 적용하며, 이미 지급한 금액은 유지한다.
- 동시 수정(409)은 덮어쓰지 않는다. 초안을 유지하고 최신 정책 다시 불러오기를 제공한다.
- 현재 정책 버전과 지급 보류 상태는 최신 조회 결과를 표시한다. 편집 전에는 금액·상품도 최신값을 사용하고, 편집을 시작하면 초안과 저장 기준 revision을 고정한다.
- 지급 보류/재개는 별도 사유와 확인을 거친다. 과거 약정 금액을 수정하지 않는다.
- 지급 보류/재개 성공은 정책 초안을 초기화하지 않는다. 정책 버전이 그대로일 때만 초안의 revision을 전진시키며, 다른 관리자의 새 정책 위로 과거 초안을 자동 덮어쓰지 않는다. 확인창을 연 뒤 상태가 바뀌면 처음 확인한 revision으로 충돌을 검출한다.
- 정책 이력, 지급 내역, 결제 수신 내역을 커서 페이지로 조회한다. 지급·수신 재처리는 사유와 확인을 거치며 임의 지급 기능이 아니다.
- 보상은 기존 환급용 적립금에 합산한다. 본인 100일 챌린지 만기 때 함께 환급하며 학습 상한과 무관하게 추가된다(50,000원 + 3,000원 = 53,000원). 별도 레퍼럴 지갑을 만들지 않는다.
- 적립은 실제 송금 완료가 아니다. 검토 사유를 보여주고 과거 금액을 다시 계산하지 않는다.
- 모바일은 한 열 카드, 데스크톱은 두 단계 나란히 배치한다. 표는 가로 스크롤 영역으로 제한한다.

## 초대인 보상 한도.

- BE #310의 `inviterLimit`을 사용해 `제한 없음` 또는 `금액 한도 적용`을 선택한다. 초대 수 제한은 설정할 수 없다. 제한 없음은 `UNLIMITED`와 null, 금액 한도는 `TOTAL_AMOUNT`와 0 이상의 안전한 정수로 저장한다.
- `초대 적립금 한도 (원)`으로 금액을 입력한다. 제한 없음에서 금액 한도로 바꾸면 값을 새로 입력해야 한다. 과거 초대 수 정책을 읽은 경우 자동으로 금액으로 변환하지 않고 금액 한도 또는 제한 없음을 선택해야 저장할 수 있다. 정책 이력의 과거 초대 수는 사실대로 표시한다. 0은 추가 초대인 지급 중단으로 명시한다.
- 가입·첫 결제에서 초대인으로 받은 금액만 평생 합산한다. 피초대인으로 받은 가입·결제 보상은 자신의 한도에서 제외한다. 남은 한도만 지급하고 한도 하향으로 기존 적립금을 회수하지 않는다고 안내한다.
- 저장 확인창에 기존 한도 → 변경 한도를 표시한다. 단계 정책의 이후 등록자 적용과 한도의 다음 지급 적용을 구분한다. 정책 이력에도 당시 한도 방식을 표시한다.
- 지급 내역은 `약정 금액`과 `현재 적립`을 구분하고 `INVITER_LIMIT_REACHED`를 `초대인 한도에 따라 부분 또는 0원 지급`으로 안내한다. 재처리나 한도 상향으로 소급 증액되지 않는다.
- 서버 응답에 한도 필드가 없으면 사용할 수 없는 상태로 표시한다. 기존 단계 정책은 수정할 수 있지만 한도 선택은 비활성화하고 요청에도 한도를 추가하지 않는다. 이를 무제한으로 표시하거나 새 한도가 저장됐다고 알리지 않는다.
- 보류·재개, 충돌과 백그라운드 조회에도 기존 정책 편집과 같은 방식으로 한도 초안을 보존한다. 기존 화면 컴포넌트와 디자인 토큰을 사용하며 별도 Figma 프레임은 없다.

검증: 단계 대상/금액 변환, 잘못된 금액·상품, 저장 확인·충돌 유지·보류/재처리 흐름을 네트워크 경계 기반 테스트로 확인한다.

## 검증 결과.

- BE #310 커밋 `020eb8d3`의 OpenAPI에서 `generate-referral-api-types.mjs`로 레퍼럴 API 타입을 재생성했다. 기존 다른 기능의 생성 스키마는 바꾸지 않았다. `UNLIMITED`의 nullable `value` 누락만 `schema-patch.ts`에서 보정했다.
- Node 22에서 전체 74개 파일·552개 테스트와 TypeScript·ESLint·Prettier·Next 프로덕션 빌드가 통과했다. 레퍼럴 관련 4개 파일·33개 테스트에 금액 한도 저장, 초대 수 설정 차단, 0원·잘못된 값, 한도 해제, 구버전 응답, 부분 지급과 정책 이력을 포함한다.
- 보류·재개, 동시 수정 충돌, 백그라운드 조회에도 편집한 금액 한도와 저장 기준 revision을 보존한다.
- 독립 리뷰에서 BE 계약과 금액 전용 설정을 대조하고 관련 33개 테스트를 다시 실행했으며, 수정이 필요한 결함은 발견하지 않았다. DB 스키마·마이그레이션·DB 접근 코드 변경은 없다.
- 로컬 모의 응답으로 1440px·390px 화면, 15,000원 → 5,000원 저장 확인, 500원 부분 지급 표시를 검증했다. 실제 BE 연동·운영 데이터 변경·배포 검증은 아니다. 별도 레퍼럴 Figma 프레임은 제공되지 않았다.
